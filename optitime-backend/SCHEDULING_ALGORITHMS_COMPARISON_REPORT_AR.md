# تقرير_مقارنة_خوارزميات_الجدولة

## 1) النطاق
هذا التقرير يشرح كيف تعمل خوارزميتا الجدولة في هذا المشروع (`Backtracking` و`Genetic Algorithm`) ويقارن بين زمن التنفيذ وجودة المخرجات اعتمادًا على الإعدادات الحالية وقاعدة البيانات الحالية.

لقطة الإعدادات الحالية:
- حد وقت `Backtracking` (`max_seconds`): `300.0`
- حد وقت `Genetic Algorithm` (`max_seconds`): `10.0`
- المصدر: `config/optitime.php`

## 2) كيف تعمل خوارزمية Backtracking (التنفيذ الحالي)
الملف الرئيسي: `app/Scheduling/BacktrackingScheduler.php`

التدفق:
1. تبني الحالة الابتدائية للتعيينات من الجلسات المثبتة (`solve()`).
2. تجهّز مسبقًا كل المرشحات القانونية لكل حدث غير مثبت (`prepareCandidatePools()`):
- تصفية مبكرة حسب القيود الصلبة قبل الدخول في الاستدعاء التراجعي (حالة القاعة/السعة/المعمل/عتبة السعة/توفر المدرّس).
- ترتيب المرشحات بنقاط soft مع قواعد ترتيب ثابتة.
3. تجري فحوصات استحالة مبكرة (`precheckImpossible()`).
4. تنفّذ بحث DFS (`search()`) مع:
- اختيار المتغير الأكثر تقييدًا أولًا.
- خرائط تعارض داخل الذاكرة (قاعة/مدرس/شعبة/يوم).
- `forward checking` على الأحداث المتأثرة.
- تخزين حالات الفشل (`failed-state cache`).
- كسر التناظر (`symmetry pruning`).
- حدود إيقاف صارمة (وقت/عدد تراجعات/عدد خطوات).
5. عند إيجاد حل كامل feasible، تطبق تحسينًا soft محليًا (`localSoftImprove()`) ثم تعيد النتيجة.

سلوك مهم:
- تتوقف عند أول جدول صالح كامل (ثم تحسين محلي فقط).
- لا تستمر في استكشاف شامل لكل البدائل بعد قبول أول حل صالح.

## 3) كيف تعمل الخوارزمية الجينية GA (التنفيذ الحالي)
الملف الرئيسي: `app/Scheduling/GeneticScheduler.php`

التدفق:
1. تبني مسبقًا مجموعة مرشحات لكل حدث (`buildCandidatePool()`) مع تطبيق مرشحات القيود الصلبة.
2. تنشئ Population ابتدائي (`randomIndividual()` + `repair()`).
3. في كل جيل (`solve()`):
- تقييم كل فرد عبر hard constraints + soft penalty.
- الاحتفاظ بـ `elites`.
- إنتاج أبناء عبر `tournament selection` + `crossover` + `mutation` موجه + `repair`.
4. تتوقف عند تحقق أحد الشروط:
- الوصول لحد الوقت،
- الوصول لحد الأجيال،
- أو تحقق شرط تقارب/توقف مبكر.
5. تعيد أفضل فرد تم الوصول إليه ضمن الميزانية الزمنية.

سلوك مهم:
- خوارزمية مدفوعة بالميزانية الزمنية وتستكشف بدائل كثيرة.
- جودة النتيجة تعتمد بشدة على إعدادات GA والوقت المتاح.
- ممكن أن تتفوق نوعيًا في بعض البيانات، لكن ليس بشكل مضمون دائمًا.

## 6) أيهما يعطي نتائج أفضل وأكثر دقة؟

- في القياسات الحالية: كلاهما `hard_violations = 0`.

### الجودة (القيود الناعمة)
على البيانات الحالية:
- `Backtracking` أعطى جودة soft أفضل (Penalty أقل): `471.77` مقابل `1323.92` تقريبًا لـ `GA`.

تفسير:
- في الحالة الحالية تحديدًا، `Backtracking` أسرع وأفضل جودة.
- هذا ليس قانونًا عامًا؛ يتغير حسب البيانات والإعدادات.

## 7) ملخص مقارنة عملي
Backtracking:
- المزايا: سرعة جيدة للوصول لحل feasible، سلوك أكثر حتمية، pruning قوي، مخاطر أقل لفشل hard.
- العيوب: ليس محسنًا عالميًا واسع البحث بعد الوصول لأول حل صالح.

GA:
- المزايا: مساحة بحث أوسع واستكشاف بدائل أكثر.
- العيوب: أعلى تكلفة زمنية، والجودة شديدة الحساسية للـ tuning والميزانية الزمنية.

## 8) التوصية بالحالة الحالية
بناءً على النتائج الحالية:
- اجعل `Backtracking` الخيار الافتراضي لتوليد الجدول الأسبوعي عندما تكون الأولوية للسرعة وجودة النتائج الحالية.
- احتفظ بـ `GA` كخيار بديل للتجارب والـ tuning.
- إذا كان الهدف أن يتفوق `GA` نوعيًا، فهو يحتاج tuning إضافي خاص ببياناتك (population/generations/mutation/repair/termination).
